# Offline snapshots

The app downloads the authenticated `/api/offline/snapshot` response into
Cache Storage. Sign in while connected once on each device to download the
snapshot; the offline login verifier uses the scrypt hashes included in the
snapshot. The server refuses to return a user file containing unsupported or
plaintext password values.

For devices on the same LAN, build or run the frontend with
`VITE_API_BASE_URL` set to the backend's reachable LAN URL, for example
`http://192.168.1.20:5000`. The Flask server must listen on a network interface
and its `CORS_EXTRA_ORIGINS` must include the frontend's exact origin.
Cache Storage and service workers require a secure browser context; when the
browser blocks an HTTP LAN origin, use HTTPS or a same-origin reverse proxy.

The **Offline Data & Sync** page can export a server package and import that
JSON file on a device that cannot reach the backend. The package contains
all record data and salted password hashes, never plaintext passwords. Export
is restricted to accounts with the `*` permission. Anyone with an imported
package can use its included account hashes for offline login, so transfer and
store it only on trusted devices and through a trusted channel.

Snapshots are stored under a username-specific Cache Storage key. Logging out
deletes that user's snapshot; an expired offline session or server session also
deletes it. When another user signs in on the same browser, snapshots belonging
to other usernames are removed before a new online snapshot is downloaded.
After logout, reconnect and sign in again to restore that user's offline data.

Every queued offline operation stores its creating username. The sync engine
sends an operation only when that username matches the currently signed-in
user; missing-owner and other-user operations stay queued. Before logout, the
app offers to sync the current user's pending operations. If the user logs out
without syncing, or sync cannot finish, those operations remain in IndexedDB
and will only be eligible to sync under their original username.

Offline last-write-wins currently uses the edit timestamp generated by each
device's clock; the server stores that timestamp when replaying the change.
It does not assign a monotonic record version. Clock skew can therefore make a
newer edit appear older and be rejected, or make an older edit appear newer and
win. Keep device clocks synchronized before editing offline. The server
serializes replay per record, but this does not remove client clock-skew risk.
